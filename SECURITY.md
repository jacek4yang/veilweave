# Security policy

veilweave is a security-sensitive project: it terminates an authenticated
proxy tunnel, mediates outbound traffic, and is meant to be run by individuals
protecting their connectivity. We take reports seriously.

## Supported versions

| Crate                | Version          | Supported          |
|----------------------|------------------|--------------------|
| `veilweave`          | `0.1.x` (main)   | :white_check_mark: |
| `veilweave-sub`      | `0.1.x` (main)   | :white_check_mark: |
| `veilweave-tools`    | `0.1.x` (main)   | :white_check_mark: |

Older versions are not patched. Please upgrade.

## Reporting a vulnerability

**Please do not file a public GitHub issue for security-sensitive bugs.**

Send a private report to one of the following channels (in order of preference):

1. **GitHub Security Advisories**: open a [draft security advisory][adv] on this
   repository. The maintainers are notified privately.
2. **Email**: contact the maintainer listed in [`CODEOWNERS`](CODEOWNERS).

We will acknowledge within 72 hours. Please include:

- A clear description of the issue and its impact.
- A minimal reproduction (`wrangler tail` excerpt + a sample `vless://` URL is fine).
- The commit/tag you reproduced against.
- Whether you intend to disclose publicly, and on what timeline.

[adv]: https://github.com/<owner>/veilweave/security/advisories/new

## Cryptographic claims

The protocol claims — and what is verified by the code — are:

- The encrypted stream is byte-for-byte interoperable with xray-core's
  `mlkem768x25519plus` profile (ML-KEM-768 + X25519, AES-256-GCM, 1-RTT).
- The signed UUID uses HKDF-SHA256 → HMAC-SHA256 keystream + 5-byte MAC;
  the comparison is constant-time.
- The relay validates `SECRET_KEY` at startup; a missing or empty value yields
  `500 not configured` (no fallback secret is ever hard-coded).

What is **not** in scope of this project:

- 0-RTT session resumption is *intentionally* not implemented (the readme
  explains the trade-off).
- ChaCha20-Poly1305 is *intentionally* not implemented (WebCrypto has no
  ChaCha20; software ChaCha in wasm32 would blow the 10 ms CPU budget).

## Operational hygiene

A few things you should do once you deploy:

- **Rotate `SECRET_KEY`** if you ever leak the relay secret. There is no
  key-rotation API; deploy a fresh `wrangler secret put SECRET_KEY` value
  generated by `veilweave-tools gen-secret`.
- **Use `wrangler secret put`** for the relay's `SECRET_KEY` in production
  — do not commit the live value to `wrangler.toml`. The committed
  `wrangler.toml` ships with a clearly-labeled placeholder.
- **Lock the subscription token** (`SUBSCRIPTION_TOKEN`) to a high-entropy
  random string.
- **Monitor `wrangler tail`** for `"vegress… rejection"`-style errors after
  rolling out a new key. A spike in MAC failures indicates UUIDs still
  signed under the old key are still in use.

## Out of scope

- Bugs in xray-core, v2ray, sing-box or any client.
- Bugs in the Cloudflare Workers runtime itself.
- Network-layer fingerprinting or censorship of the WS endpoint.
